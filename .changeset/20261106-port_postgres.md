**safebyok-postgres is rewritten onto the new VaultDB.** `postgresVaultDB(opts)` gives way to `new PostgresVaultDB({ client, listen?, maxBoxes?, maxRecordBytes? })`, a `VaultDB` from `safebyok/storage`; `client` runs `query` and `transaction`, which a PGlite does as it is and `pgClientOf(pool)` makes of a `pg` Pool. The per-request `user_id` gate is gone: the route that builds each scope decides who reaches which bank. **Stored format:** two tables, `safebyok_vaults` and `safebyok_boxes`, each row's record one `jsonb` column beside the columns it is keyed by; `safebyok_vault_tombstones`, the foreign key and the column-per-field layout are gone, and so are `VaultNotifySql` and its triggers: each write now sends its own notification on its user's channel, `vaultChannelOf(user_id)` (`safebyok_` and the user_id), which `listen` hears: a vault's notice is its row as stored, a box's one JSON array of its vault's fields without the wayins, then its own, a ciphered field as `[iv, ciphertext]`, and a row too long for a notification is told by where it is and read afresh; the README's recipe LISTENs on a channel the first time a watch asks and never UNLISTENs. A channel is at most 63 bytes, so for a user_id of more than 54 characters every write that would send a notice refuses as `storage_unavailable` (cause: `channel name too long`). Drop the old tables and run `VaultTablesSql` again; no vault stored before is read. A failed statement refuses as `storage_unavailable`, or `unexpected_error` for a missing table or privilege, its cause only the driver's message and code. **`safebyok/storage` exports `Checker`, `Checkers` and `objCheck`**, with the types `ObjCheckOpts` and `Refusing`, for an adapter's own options and rows. **`Notice.world` may be null**: a watch hears a box with a null world when its store's notice came without the vault row, as a PostgresVaultDB's does, and `Heard.vault` is optional to match; a listing then takes the box alone. `describeVaultDBBattery` takes `boxNoticesCarryVault: false` for such a store.
