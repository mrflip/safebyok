**Every VaultDB verb does one thing, transactionally; a vault carries a `vault_epoch`, and deleting it leaves a tombstone.** `VaultProps` gains `vault_epoch`, a counter the store moves up by one on every write of the gate (`putVaultProps`) and on `delVault`, whatever value the writer sends; no box write moves it. `delVault(scope, expected)` now expects `{ vault_tok, gate_epoch }` (a delete proven against a gate another device has since changed refuses as `stale_write`; `delDamagedVault` expects the `vault_tok` alone, as the props it deletes show no `gate_epoch`) and leaves a **tombstone**, `{ format: 'safebyok-tombstone-v1', ...scope, vault_epoch }`, in the vault's place, which it resolves. A tombstone holds no `vault_tok`, so it meets no expectation: every write over it refuses as over no vault, a second `delVault` included, and `getVault` reads it as no vault. `ensureVault(draft)` takes one argument, the gateless draft (which names its scope and claims `vault_epoch` 0), and over a tombstone starts a new life under the draft's fresh `vault_tok` with the counter carried on. `putVaultProps` resolves the vault props as stored. `DeviceDB.putLease(record)` resolves the record as stored, and one scope's calls land in the order they were made (the interface states it and `describeDeviceDB` checks it); `idbDeviceDB`'s `getLease` no longer deletes a lease a newer `putLease` wrote after it found the row unreadable. **Gone:** `getVaultProps`, `ensureVaultProps`, `listBoxes`, `listBoxRecords` and the `doGetVaultProps`, `doEnsureVaultProps` and `doListBoxes` hooks, with `Expectations.vaultTokMeets`; read a vault through `getVault` and `ensureVault` (`getVaultRecords` and `ensureVaultRecords` for a server). **An adapter of your own** implements `doPutVaultProps` to resolve the stored props, `doDelVault` to resolve the tombstone (null for a miss), and `doEnsureVault` to carry the counter over a tombstone; `Expectations.vaultPropsPutOf`, `newLifeOf`, `tombstoneOf` and `isTombstone` make the records for a key-value store. **What a host sees of vaults stored before:** their props carry no `vault_epoch`, so each reads as `damaged_vault` (the format string is unchanged; there is no migration before 1.0): `delDamagedVault` clears it where the backend can hold it, and each user makes their vault anew. **Postgres** hosts drop their tables and run `VaultTablesSql` again (a `vault_epoch` column on `safebyok_vaults`, and the new table `safebyok_vault_tombstones`); the route recipe's `ensureVault` takes `[draft]`, and its `listBoxes` and `getVaultProps` verbs are gone. **Convex** hosts re-export the nine functions (`getVaultProps`, `ensureVaultProps` and `listBoxSummaries` are gone) and deploy the component, whose `putVaultProps` answers the props as stored and whose `delVault` answers the tombstone. **A GraphQL** server and its clients deploy together: `safebyokEnsureVault` takes the draft alone, `safebyokPutVaultProps` answers the stored props in a landed body, `safebyokDelVault` answers a `SafebyokTombstone` and expects an optional `gate_epoch`, and `safebyokGetVaultProps`, `safebyokListBoxes` and `safebyokEnsureVaultProps` are gone; a `ServedVaultDB` of its own drops the removed verbs. **The vault, meanwhile**, creates itself as before, now in two writes (`ensureVault` of the gateless vault, then its first gate): a first unlock that finds gateless props another device ensured sets its passphrase over them, where it refused as `created_elsewhere` ("has not set its passphrase yet"); `del()` expects the gate it read. **A server that restores a backup must wipe the restored vaults** (the core README says why).
