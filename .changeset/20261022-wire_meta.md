**What a refused GraphQL write learned now travels in the mutation's body, never in an error's `extensions`.** GraphQL servers, gateways and APM tools commonly log error extensions, and a stale update of the vault props learned the winning vault props, both ways in with their salts and wrapped vaultKeys: offline-guessing material for whoever reads those logs. `safebyokPutVaultProps` now resolves `SafebyokPutVaultPropsAnswer` (`landed`, and for a `stale_write` the `refusalkind`, the `message` and `vault_props_stored`) in place of a `Boolean`, and `safebyokPutBox` resolves `SafebyokPutBoxAnswer` (`landed` and `box_stored`; for a `stale_write` or a `vault_full`, also the `refusalkind`, the `message`, and `box_stored` or `capacity`) in place of a `SafebyokBox`; the new `SafebyokStoredRecord` scalar carries a stored record, sound or damaged, as it is. Every other refusal still crosses as a GraphQL error, its `extensions` now holding `kind` alone (`extensions.meta` is gone). `graphqlVaultDB` reads the body and throws the same VaultError as before, `meta` included, so a vault's code and the VaultDB conformance suite are unchanged. **Redeploy the GraphQL server and the app's client together** (no compatibility before 1.0): a client and a server of different versions refuse each other's operations as `bad_option`, the message saying to serve `VaultSchemaSdl` from the client's version; re-register the changed `safebyokPutVaultProps` and `safebyokPutBox` documents in `VaultOperations` if your server allows only listed operations. The VaultDB layer's `err.meta` is unchanged.
