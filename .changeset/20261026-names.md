**`user_id` everywhere, spelled as it is stored.** The signed-in user's id is `user_id` in every option and prop, as in a scope and in storage; `userId` is gone. A host renames it where it passes one: `bank.ensureVault({ user_id, vaultlabel })` and its siblings (`reopenVault`, `closeVault`, `clearCachedVault`, `delDamagedVault`, `entryOf`), where `{ userId }` now refuses `bad_option` naming `user_id`; `delDamagedVault({ ...bankOpts, user_id, vaultlabel })`; safebyok-react's `<BankProvider user_id={...}>`; safebyok-postgres's `postgresVaultDB({ client, user_id })`; and, in tests, `safebyok/testing`'s `memoryVaultOpts({ user_id })` and the options it hands back. A `postgresVaultDB` still handed `userId` reads as no one signed in, and refuses every call `identity_revoked`: TypeScript flags the old name at the call. safebyok-react's `messages.passphraseUsername(user_id, vaultlabel)` takes the same value as before. Nothing stored changes.

**A passkey's answer spells its fields as the wayin stores them.** `PasskeyAnswer` is `{ credential_id, prf_salt_b64, prfBytes }`, where it was `{ credentialId, prfSaltB64, prfBytes }`: the same values the snapshot's `passkey` shows under the same names. safebyok-react's `askPasskey` and `createPasskey` make the new shape, so a host that passes their answer straight to `gating.attemptPasskey` or `vault.putWayin` changes nothing; one that builds an answer itself renames the two fields, and the old names refuse `bad_option`.

**The snapshot's `askPassphraseAt` is `ask_passphrase_at`**, as the lease stores it, and so is the Vault object's getter: `vault.getSnapshot().ask_passphrase_at` and `vault.ask_passphrase_at`, the same instant (epoch milliseconds, null while locked). A host reading the old name reads `undefined`; TypeScript flags it.

**The adapters' wire arguments name a vault by its three names, flat.** Every function or root field aimed at a vault takes `applabel`, `user_id` and `vaultlabel` as arguments of their own beside the rest, where it took one nested `scope`: safebyok-convex's `getVault`, `getBox`, `putBox`, `getCapacity`, `delBox`, `delVault` and `watchVault` take `{ applabel, user_id, vaultlabel, boxlabel, expected }` and the like, and each still refuses `identity_revoked` unless the host's `getUserId` answers that `user_id`, the very field the component then reads; safebyok-graphql's `safebyokGetVault`, `safebyokGetBox`, `safebyokGetCapacity`, `safebyokPutBox`, `safebyokDelBox`, `safebyokDelVault` and `safebyokVaultChanged` take three `String!` arguments, and `SafebyokVaultScopeInput` is gone. `ensureVault` and `putVaultProps` take their records as before. What a host does: deploy the server and the browser's package together, as for any change to the SDL or the Convex functions. A browser and a server a version apart refuse each other's calls at the argument check (Convex's validator, or GraphQL's), and the user sees `storage_unavailable`, or `bad_option` from a GraphQL server that marks the error `GRAPHQL_VALIDATION_FAILED` or `BAD_USER_INPUT`, as safebyok-graphql's README says; nothing stored changes. A host that registers `VaultOperations` as persisted operations registers them again. `graphqlVaultDB` now refuses `storage_unavailable` when a server answers without the vault it was asked for, where it read that as no vault.
