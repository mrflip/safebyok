**`user_id` everywhere, spelled as it is stored.** The signed-in user's id is `user_id` in every option and prop, as in a scope and in storage; `userId` is gone. A host renames it where it passes one: `bank.ensureVault({ user_id, vaultlabel })` and its siblings (`reopenVault`, `closeVault`, `clearCachedVault`, `delDamagedVault`, `entryOf`), where `{ userId }` now refuses `bad_option` naming `user_id`; `delDamagedVault({ ...bankOpts, user_id, vaultlabel })`; safebyok-react's `<BankProvider user_id={...}>`; safebyok-postgres's `postgresVaultDB({ client, user_id })`; and, in tests, `safebyok/testing`'s `memoryVaultOpts({ user_id })` and the options it hands back. A `postgresVaultDB` still handed `userId` reads as no one signed in, and refuses every call `identity_revoked`: TypeScript flags the old name at the call. safebyok-react's `messages.passphraseUsername(user_id, vaultlabel)` takes the same value as before. Nothing stored changes.

**A passkey's answer spells its fields as the wayin stores them.** `PasskeyAnswer` is `{ credential_id, prf_salt_b64, prfBytes }`, where it was `{ credentialId, prfSaltB64, prfBytes }`: the same values the snapshot's `passkey` shows under the same names. safebyok-react's `askPasskey` and `createPasskey` make the new shape, so a host that passes their answer straight to `gating.attemptPasskey` or `vault.putWayin` changes nothing; one that builds an answer itself renames the two fields, and the old names refuse `bad_option`.
