The VaultDB contract's tightening, in one place: what a host does who writes its own VaultDB adapter, uses one of ours, or catches refusal kinds. Nothing stored changes, so no vault, lockbox or device needs migrating; this release's other entries say each change in full.

If you use an adapter of ours (`localVaultDB`, `idbVaultDB`, `safebyok-postgres`, `safebyok-convex`, `safebyok-graphql`), upgrade its package with the core and change nothing else, with two exceptions. Over GraphQL, `safebyokUpdateBox` answers a `SafebyokLockbox` where it answered `Boolean!`, and `safebyokRetireBox` takes a `SafebyokLockboxRetireExpectationInput` and answers a `SafebyokLockboxRetirement` (its `outcome` is the enum `SafebyokRetireOutcome`), so your GraphQL server and its browsers move to this version together. A Postgres route recipe's two halves, the server's and the browser's, move together likewise. The Convex component's `updateBox` and `retireBox` mutations answer the stored lockbox or the outcome, or null, in place of true or false.

If you write your own VaultDB adapter, three of its methods change. `doUpdateBox` resolves the lockbox as stored, read back in the same atomic step as the write, where it resolved true, and null where it resolved false: only null now means the write was stale. `doRetireBox` takes a `LockboxRetireExpectation`, `{ vault_id, revision_tok }`, and resolves a `LockboxRetirement`, `{ outcome: 'retired' | 'retired_other' | 'absent' }`, from the same atomic step as the removal, and null where it resolved false (`Expectations.retirementOf` compares for a key-value store). An adapter still resolving true or false meets `corrupt_record` on every lockbox write or retirement. `describeVaultDB` now expects `bad_record` of an adapter's wrapper, so run it over your adapter. The Vault warns through the host's logger when a retirement removed another revision than the one it showed (`retired_other`), and `idbVaultDB` no longer rings its change bell, which tells other tabs to read again, for a retirement that found nothing (`absent`).

If you catch refusal kinds: a record or expectation handed to a VaultDB verb that this package does not build, which was `bad_option`, is now `bad_record` (family `misuse`, beside `bad_option`, which keeps every other use). A host that branches on `bad_option` to catch a bad record from a VaultDB it calls directly adds `bad_record`. `isVaultCondition` is false for both, so an error boundary treats them alike.

Two cautions for a host's own code. A lockbox's sidecar is visible in storage: authenticated, but never encrypted, so keep secret material out of it. And do not overlap your own `storeBox()` calls on one lockbox: storage cannot tell your second call from another device's write, so it is refused as `stale_write`.
