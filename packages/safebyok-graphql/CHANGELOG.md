# safebyok-graphql

## 0.4.0

### Minor Changes

- [#125](https://github.com/mrflip/safebyok/pull/125) [`80673f9`](https://github.com/mrflip/safebyok/commit/80673f9d073f592b111a9144df1a3eb26e394e6c) Thanks [@mrflip](https://github.com/mrflip)! - **Every adapter now compares a lockbox write's `vault_key_epoch`** (VAULTDB.md line 3.8): `idbVaultDB` in the write's transaction, the Convex component's `updateBox` mutation, and `postgresVaultDB` in the write's one statement, reading the vault's bundle row `FOR SHARE`; `graphqlVaultDB` gets it from the VaultDB its server serves. A lockbox write sealed under a vaultKey the bundle no longer stands for now refuses as `stale_write`, writing nothing. Every vault is at `vault_key_epoch` 1 today, so no write a host makes now is refused by it. Convex hosts redeploy the component to take it up.
  
  **Postgres: a bundle update waits for lockbox writes in flight.** The `FOR SHARE` read is a shared lock: lockbox writes never wait for each other on the bundle (two writes to one boxlabel still meet at its row, as before). A hard-cap trigger that takes `FOR UPDATE` on the vault row, as the one in 0.3.0's README did, deadlocks two first writes into one vault, one of them failing as `storage_unavailable`: what becomes of it is in this release's entry "The vocabulary reform, in one place".
  
  **`safebyok/testing`: `describeVaultDB` no longer takes `comparesVaultKeyEpoch`.** Line 3.8's tests run for every adapter; drop the option, and compare the epoch in your adapter's lockbox write.
  
  **`close()`, and a refresh that outlives the key, now stop a read in flight.** A `read()` or `use()` under way when the handle is closed hands back nothing and refuses with `vault_closed`; one under way when a refresh finds the vault's ways in changed on another device, or the vault gone, refuses with `vault_locked`. A `lockSoon()` grace running out, and a clock that cannot be read, still let a read in hand finish.
  
  **A device-store failure says what failed.** Still kind `storage_unavailable`, the device store's error its cause, but the message now names the step -- reading or writing the remembered unlock, reading or writing this device's mark of the vault, erasing either -- and what to do. `eraseDamagedVault` now reports a device-store failure the same way (it threw the device store's own error before).

- [#125](https://github.com/mrflip/safebyok/pull/125) [`6f037b4`](https://github.com/mrflip/safebyok/commit/6f037b43bcf3c7041280b6fa9966551ec85227f7) Thanks [@mrflip](https://github.com/mrflip)! - Names are held to a floor, the key-value stores join their ckeys on `^`, and the `VaultDB` verbs take no validators.
  
  - **A vault kept in `localVaultDB` or `idbVaultDB` before this release reads as absent** (its rows, filed under the old JSON-tuple ckeys, are left as they were), and a remembered unlock or device mark in `idbDeviceDB` is swept: the user unlocks, or makes the vault, again. Rows are now filed under `kind^applabel^user_id^vaultlabel[^boxlabel]` (`Ckeys`, whose functions are as before, with `Ckeys.Delimiter`).
  - **Every `VaultDB` verb loses its trailing `validators` argument.** A server or wrapper calling them drops it. Each verb holds every name to the floor and to a fact every adapter now declares, `maxNameBytes` (VAULTDB.md 7.3): an adapter of your own adds it. Postgres declares 640 bytes, and the GraphQL client the same.
  - **The floor** (`NameFloor`, `NoteFloor`, exported with `NameFloorBytes` and `NoteFloorBytes`): every name is one character to 1 KiB of UTF-8, every note at most 4 KiB, each well-formed Unicode in NFC with no control character (a note may hold tab and newline), and no name holds `^`, which the key-value stores join names on, whatever validators a host passes and whatever store holds the vault. A stored record below it reads back as damaged. `AnyTextValidators` is now the floor itself, so it refuses an empty name, a control character, a `^` or text not in NFC, as it did not before. A host on Convex, Postgres or GraphQL whose names hold `^` meets `bad_label` at `openVault`: there is no option to join on another character.
  - **A host's validators run at the vault's entry only**: a lockbox stored under a name or note they refuse now lists, reads and erases as sound, where it listed as damaged.
  - **`UserId`'s default is 1 to 100 ASCII letters, digits and `-_.:@+|`** (`UserIdPattern`), refusing spaces, other punctuation and text outside ASCII it used to admit: a host whose ids hold more passes its own `validators.userId`.
  - `listBoxes` sorts by code unit, never by the runtime's locale.

- [#125](https://github.com/mrflip/safebyok/pull/125) [`443e7f6`](https://github.com/mrflip/safebyok/commit/443e7f68ab088fb290c62a37712c44d6bd67f18d) Thanks [@mrflip](https://github.com/mrflip)! - **Stored shape: a lockbox's note becomes a public bag of any JSON, and the lockbox reserves its whisper's codec and schema version.** The lockbox's format is `safebyok-lockbox-v3`. No lockbox written before this reads: no compatibility before 1.0. A `safebyok-lockbox-v2` lockbox lists as damaged (`{ boxlabel, damaged: true }`) and `read()` refuses it as `damaged_lockbox`; `erase()` it, or `store()` over it, which writes it afresh. The bundle, the unlock envelopes and the device records are unchanged, so a vault still opens and unlocks.
  
  - **`safebyok`**:
    - `store(boxlabel, whisper, { public })` takes the lockbox's **public bag**, any JSON value (`PublicBag`, exported), shown in the snapshot while locked as `box.public` and never interpreted by the vault. Left out, the lockbox keeps the bag it has, and a new lockbox gets `{}`; `{}` empties it. A bag JSON cannot carry is refused as `bad_option`. `opts.note` is gone: a host keeping a note moves it into the bag, as `{ public: { note } }`, and checks its bag's shape itself before `store()`.
    - The bag is stored as its JSON, keys sorted, in the lockbox's `public_json`, always written, and bound into both of the lockbox's encryptions with every other field of its header, so a bag altered or swapped in storage makes the lockbox refuse to open. The lockbox also records `whisper_codec` (`'json_v1'`) and `whisper_schema_version` (`1`), bound the same way. `LockboxSummary` carries `public` in place of `note`, and none of the three stored fields.
    - The stored `public_json` must be exactly the vault's own serialization (keys sorted, no spacing): a lockbox whose bag was respaced, reordered or nested too deep in storage lists as damaged. And a `store()` over a lockbox that will not decipher (its ciphertext, bag or times altered in storage) carries neither its bag nor its `registered_at` forward: the bag becomes `{}` unless one is given, and `registered_at` is now.
    - `maxWhisperBytes` counts the whisper's JSON and the bag's together, so a whisper of exactly `maxWhisperBytes` no longer fits beside even the empty bag's two bytes. A replacement is never refused as `vault_full` any more: it weighs what it replaces.
    - The note's checks go: `LockboxNote`, `MaxNoteChars`, `NoteFloor` and `NoteFloorBytes` are no longer exported, and `VaultValidators`, `DefaultValidators` and `AnyTextValidators` have no `note` field. A `validators` bag holding `note` is refused as `bad_option`, as any field the vault does not know is.
    - A lockbox's format is bound into its encryptions once, as the binding's leading tag, and no longer again inside its header.
  - **`safebyok-convex`**: the component's lockbox validator takes `safebyok-lockbox-v3` only, with `whisper_codec`, `whisper_schema_version` and `public_json` in place of `note`, so a deployment holding lockboxes written before this no longer matches its schema: delete the component's lockbox rows (or clear its tables) before deploying it.
  - **`safebyok-postgres`**: `safebyok_lockboxes` loses `note` and gains `whisper_codec` (text), `whisper_schema_version` (bigint) and the bag's JSON as text, never jsonb, which would rewrite the bound text (`sidecar_json`, as the release ships it), each `NOT NULL`. A database made before this release drops the tables and lets `VaultTablesSql` make them afresh, as this release's entry "The vocabulary reform, in one place" says.
  - **`safebyok-graphql`**: `SafebyokLockbox`, `SafebyokLockboxInput` and `SafebyokListedLockbox` lose `note` and gain `whisper_codec: String!`, `whisper_schema_version: Int!` and `public_json: String!`. A host serving the recipe's SDL deploys the new one with its server.
  - **`safebyok-react`**: `VaultProvider` passes no `note` check through, as there is none.

- [#158](https://github.com/mrflip/safebyok/pull/158) [`6f0382c`](https://github.com/mrflip/safebyok/commit/6f0382c52bf04e7ff83b1789787ab89c8cc10877) Thanks [@mrflip](https://github.com/mrflip)! - The vocabulary reform, in one place: this release renames what a host touches, and what a vault stores, to the words VOCABULARY.md defines. Nothing has a compatibility alias, and nothing stored before it is read. This release's other entries say each change in full; this is what a host does.
  
  Names. The unlock envelope is the wayin; what a device keeps to unlock again is the lease (`forcePassphraseReentryHours` is `leaseHours`); a lockbox's public bag is its sidecar; the bundle is the vault props; erase is retire (`store`, `read`, `use`, `erase` and `destroy` are `storeBox`, `readBox`, `useBox`, `retireBox` and `retire`); `revision_id` is `revision_tok`; the encryption's "binding" is its ctx. Every renamed export, option, stored field, ckey and refusal kind (`absent_wayin`, `damaged_wayin`, `last_wayin`, `too_many_wayins`, `damaged_vault`) is in `notes/old_vocabulary.md`, beside its replacement; a DeviceDB or VaultDB of your own renames its methods to match.
  
  Making a vault. `openVault(opts)` is gone, with no alias: write `const vault = Vault.make(opts)`, which returns at once, and `await vault.hello()` where you want to know the vault has settled. `Vault.make` now refuses an option it does not take as `bad_option`, naming it (and the new name of a retired one), where it used to ignore it; VaultProvider throws a prop it does not take to its error boundary the same way. A hello that cannot read storage leaves the vault `opening` with the snapshot's new `trouble` saying why, and any later call tries again.
  
  Behaviour. `storeBox()` no longer retries when another device wrote first: it catches up once and throws `stale_write` at once, for your app to decide whether to store again. A first unlock that loses the race to another device creating the vault throws the new `created_elsewhere` in place of `wrong_passphrase`: a host that says "check for typos" on `wrong_passphrase` should handle it too (safebyok-react's PassphraseModal shows it as advice).
  
  Stored formats. A host upgrading from 0.3.0 has vault props in `safebyok-vault-v2`, lockboxes in `safebyok-lockbox-v2` and a lease in `safebyok-unlock-v1`; this release writes `safebyok-vault-v3`, `safebyok-lockbox-v5` and `safebyok-lease-v1`. There is no migration, and an old record fails safe. Where an old vault's record is still found, in a VaultDB of your own, it reads as damaged (`damaged_vault`) and is retired with `retireDamagedVault()` and made afresh, and any older lockbox lists as damaged and is stored again or retired (its whisper stored again by the user). In Postgres, whose tables you drop (below), a vault written before reads as absent, and the user makes it again. So it does in `localVaultDB` and `idbVaultDB`, which 0.3.0 filed under JSON-tuple ckeys (`["vault","acme","u1","main"]`) where this release joins them on `^` (`vault^acme^u1^main`), its old rows left as they were. On the device an old lease is never read: `idbDeviceDB` deletes 0.3.0's rows, the device mark's with the lease's, unread, and a DeviceDB of your own that hands an old lease back sees the vault erase it, with one warning to the logger. Either way each device asks for the passphrase or passkey once.
  
  Postgres. There is no migration before 1.0: a database made by `safebyok-postgres@0.3.0`, or from `main` between releases, drops the package's tables and lets this release make them afresh. **This deletes every vault and lockbox stored in Postgres**: each user makes their vault again and stores their whispers anew. This replaces every Postgres step in this release's other entries. Run once, before this release's `VaultTablesSql` first runs, and with no server on the old version still running (one that runs its `VaultTablesSql` as it starts would make the old tables again):

A new error kind, `identity_revoked`, is storage saying that the user a vault was opened for is no longer the one signed in -- signed out, or another user signed in -- and the vault meets it by locking at once, as `lock()` does: its vaultKey dropped, this device's remembered unlock forgotten, the snapshot `locked`. It erases nothing stored, and the call that met the refusal throws it. A background refresh that meets it locks all the same, and tells the logger. `openVault`'s new `whenIdentityRevoked` option chooses `'lock'` (the default) or `'stay'`, which only throws, leaving the vault as before; `IdentityRevokedResponseVals` lists the two. `VaultProvider` passes the option through.

Branch on `identity_revoked` to send the user to sign in. `not_permitted` stays, for a signed-in user refused one call by a backend of your own, and locks nothing.     - The bundle's format is `safebyok-vault-v2`. It gains `vault_key_epoch` (1 for a vault's first vaultKey) and `prior_vault_key` (absent until a vault's vaultKey is replaced). Each unlock envelope gains `vault_key_epoch`, `device_id` (a random id the device that added it keeps for the vault) and `registered_at`, all bound into its wrap. - [#120](https://github.com/mrflip/safebyok/pull/120) [`18a960b`](https://github.com/mrflip/safebyok/commit/18a960b5ff9d240643bf05e5a166d95d3a1d70fb) Thanks [@mrflip](https://github.com/mrflip)! - **`describeVaultDB` races its writers from two devices, under every interleaving it can make** (`safebyok/testing` grows).
