- [#580](https://github.com/mrflip/safebyok/pull/580) [`a227cfe`](https://github.com/mrflip/safebyok/commit/a227cfe56f334ab3ff72e13e0c5e1bf2bad8087e) Thanks [@mrflip](https://github.com/mrflip)! - The GraphQL schema is typed, and `GraphQLVaultDB` is a client of it checked by the core's own answer checks. Nothing here reads the old schema: deploy the server and the browser together, from the same release.
  
  * `safebyok-graphql/server`'s schema has one operation for each verb of a vaultDB, `safebyokTidyGone` among them, answering a `SafebyokTidiedAnswer`, and `safebyokWatch`. Each operation answers what the verb's `try*` form answers. Records, options and answers are typed fields. A sidecar, a damaged row and `err.meta` are `SafebyokJson`, and times are `SafebyokEpochMillis`.
  * A refusal is the answer's `err` field, never a GraphQL error: its refusalkind, its message, and a meta holding capacity, fieldnames and call alone. Its cause crosses no wire, and no longer reaches the server's logs through the resolvers.
  * The resolvers call the hosted vaultDB's own `try*` verbs, for the user the request is signed in as alone. `safebyokWatch` ends with an `identity_revoked` notice once its session is signed out, or signed in as another user.
  * `GraphQLVaultDB` is a class implementing the core's `VaultDBVerbs` over your urql Client. A GraphQL error, a client and server out of step, is `unexpected_error` with no cause, so that no GraphQL error's server text reaches your logs; a failed request stays `storage_unavailable`, its cause a fresh Error holding only the network error's name, the HTTP status and a code such as `ECONNREFUSED`: never urql's CombinedError, its message, or a response's body. A watch whose stream ends, by a closing result, an error or a refusal, tells the bank's `onBadNews` once and is not subscribed again; one ended by `identity_revoked` tells nothing more.
  * New exports: `VaultOperations` from `safebyok-graphql` itself (the documents a client sends), and the `CrossingAnswer` and `CrossingNotice` types from `safebyok-graphql/server`.
  * The README says what a host must do when the signed-in user changes: vacate the bank and make another. A bank never follows a change of user_id.
  * Breaking: the schema is rewritten, and `safebyokHeard` is gone.
  * Breaking: `VaultFieldArgs` holds each root field's typed arguments, keyed by the field's name.
  * Breaking: `GraphQLVaultDB` no longer extends `VaultDB`, and takes `{ client }` alone, refusing `maxRecordBytes` as `bad_option`: limits are set on the vaultDB your server hosts and hands to `vaultResolvers`.
  * Breaking: the `graphql` peer range is `^17.0.0`. The scalars use graphql 17's coercion hooks, which graphql 16 ignores, so on 16 the time scalar would check nothing.

### Minor Changes

- [#125](https://github.com/mrflip/safebyok/pull/125) [`80673f9`](https://github.com/mrflip/safebyok/commit/80673f9d073f592b111a9144df1a3eb26e394e6c) Thanks [@mrflip](https://github.com/mrflip)! - **Every adapter now compares a lockbox write's `vault_key_epoch`** (VAULTDB.md line 3.8): `idbVaultDB` in the write's transaction, the Convex component's `updateBox` mutation, and `postgresVaultDB` in the write's one statement, reading the vault's bundle row `FOR SHARE`; `graphqlVaultDB` gets it from the VaultDB its server serves. A lockbox write sealed under a vaultKey the bundle no longer stands for now refuses as `stale_write`, writing nothing. Every vault is at `vault_key_epoch` 1 today, so no write a host makes now is refused by it. Convex hosts redeploy the component to take it up.
  
  **Postgres: a bundle update waits for lockbox writes in flight.** The `FOR SHARE` read is a shared lock: lockbox writes never wait for each other on the bundle (two writes to one boxlabel still meet at its row, as before). A hard-cap trigger that takes `FOR UPDATE` on the vault row, as the one in 0.3.0's README did, deadlocks two first writes into one vault, one of them failing as `storage_unavailable`: what becomes of it is in this release's entry "The vocabulary reform, in one place".
  
  **`safebyok/testing`: `describeVaultDB` no longer takes `comparesVaultKeyEpoch`.** Line 3.8's tests run for every adapter; drop the option, and compare the epoch in your adapter's lockbox write.
  
  **`close()`, and a refresh that outlives the key, now stop a read in flight.** A `read()` or `use()` under way when the handle is closed hands back nothing and refuses with `vault_closed`; one under way when a refresh finds the vault's ways in changed on another device, or the vault gone, refuses with `vault_locked`. A `lockSoon()` grace running out, and a clock that cannot be read, still let a read in hand finish.
  
  **A device-store failure says what failed.** Still kind `storage_unavailable`, the device store's error its cause, but the message now names the step -- reading or writing the remembered unlock, reading or writing this device's mark of the vault, erasing either -- and what to do. `eraseDamagedVault` now reports a device-store failure the same way (it threw the device store's own error before).

- [#125](https://github.com/mrflip/safebyok/pull/125) [`6f037b4`](https://github.com/mrflip/safebyok/commit/6f037b43bcf3c7041280b6fa9966551ec85227f7) Thanks [@mrflip](https://github.com/mrflip)! - Names are held to a floor, the key-value stores join their ckeys on `^`, and the `VaultDB` verbs take no validators.
  
  - **A vault kept in `localVaultDB` or `idbVaultDB` before this release reads as absent** (its rows, filed under the old JSON-tuple ckeys, are left as they were), and a remembered unlock or device mark in `idbDeviceDB` is swept: the user unlocks, or makes the vault, again. Rows are now filed under `kind^applabel^user_id^vaultlabel[^boxlabel]` (`Ckeys`, whose functions are as before, with `Ckeys.Delimiter`).
  - **Every `VaultDB` verb loses its trailing `validators` argument.** A server or wrapper calling them drops it. Each verb holds every name to the floor and to a fact every adapter now declares, `maxNameBytes` (VAULTDB.md 7.3): an adapter of your own adds it.     - `LockboxExpectation` gains `vault_key_epoch`. `VaultDB.updateBox` lands a lockbox only while the bundle stands at that epoch (`VAULTDB.md` line 3.8), and refuses as `bad_option` a lockbox whose own epoch is not the expected one. An adapter of your own compares it in its `doUpdateBox`, beside `vault_id` and `revision_id`; `describeVaultDB` tests it, and its new option `comparesVaultKeyEpoch: false` holds that test pending for an adapter that does not yet. `localVaultDB` compares it; the IndexedDB, Convex and Postgres adapters (and GraphQL's recipe, over Postgres) do not yet. Nothing in this release replaces a vaultKey either, so every vault stands at epoch 1 and the comparison has nothing yet to refuse.
    - `DeviceDB` gains `readMark`, `writeMark` and `eraseMark`, which a host's own `DeviceDB` must implement (`openVault` refuses one without them as `bad_option`), and `eraseAll` erases marks too. A device mark (`DeviceMark`, format `safebyok-mark-v1`) holds the device's id for the vault and the highest `unlock_epoch` and `vault_key_epoch` it has seen. `memoryDeviceDB` and `idbDeviceDB` keep them; `Ckeys.mark` and `Ckeys.isMark` name their rows.
    - New error kind `rolled_back`, a condition: this device has already seen a newer copy of the vault than storage offers now, at a higher `unlock_epoch` or `vault_key_epoch`. It is refused at open, unlock, every change to the ways in and every refresh, and nothing is taken from it. A host whose storage was restored from an older copy on purpose accepts it on a device by `deviceDB.eraseMark(scope)` and opening again (the README's *A vault rolled back*). `destroy()` and `eraseDamagedVault` erase the mark.
  - **`safebyok-convex`**: the component's validators carry the new fields and formats, so a deployment holding records written before this no longer matches its schema: clear the component's tables before deploying it.
  - **`safebyok-postgres`**: `safebyok_bundles` gains `vault_key_epoch` and `prior_vault_key`, and `safebyok_lockboxes` gains `vault_key_epoch`. `VaultTablesSql` creates only missing tables, so drop and recreate tables made before this.
  - **`safebyok-graphql`**: the schema carries the new fields (`prior_vault_key` as the scalar `SafebyokPriorVaultKey`), and a lockbox expectation's `vault_key_epoch`.

### Patch Changes

- [#115](https://github.com/mrflip/safebyok/pull/115) [`2b9567b`](https://github.com/mrflip/safebyok/commit/2b9567bd51a37b8fe94c2972c8abecb27a019d41) Thanks [@mrflip](https://github.com/mrflip)! - Postgres's lockbox limit is now the contract's best effort, and its push is opt-in: the tables ask nothing of a host beyond tables, columns and keys.
  
  `safebyok_bundles` loses its `lockbox_count` column, and the count trigger, the `FOR UPDATE` row lock and the second read on a full vault go with it. A new lockbox is inserted in one statement that counts the vault's lockboxes as of its own start and says, from that one snapshot, why it missed: a vault at its limit is `vault_full`, a vault gone or a boxlabel already taken is `stale_write`, and so is a foreign key violation (`23503`) from a vault erased mid-statement. With no lock, writers racing for the last places under READ COMMITTED may each find room and all land, a few past the limit (by at most one less than the number of racers), which the contract allows (lines 4.2 to 4.5); the README says what it guarantees, that every guarantee holds at READ COMMITTED (above it some races fail with `40001`, refused as `storage_unavailable`), and offers an unsupported trigger for a host that wants a hard cap.
  
  `VaultTablesSql` no longer installs the NOTIFY trigger. A host that wants other devices' writes pushed runs the new `VaultNotifySql` (also shipped as `vault-notify.sql`) once, and passes a `listen`; without it, `subscribe` never calls, the vault refreshes after its own writes, and another device's changes arrive on its next read. A host whose tables came from an earlier build must drop the count trigger and the column (`DROP TRIGGER safebyok_lockboxes_counted ON safebyok_lockboxes` and `ALTER TABLE safebyok_bundles DROP COLUMN lockbox_count`), since the old trigger can deadlock `eraseBox` against `eraseVault` now that the adapter no longer locks the bundle row; it may then run `VaultNotifySql` to keep push; before 1.0.0 nothing migrates for you. `safebyok-graphql`'s README points at `VaultNotifySql` for subscriptions over Postgres.

- [#120](https://github.com/mrflip/safebyok/pull/120) [`18a960b`](https://github.com/mrflip/safebyok/commit/18a960b5ff9d240643bf05e5a166d95d3a1d70fb) Thanks [@mrflip](https://github.com/mrflip)! - **`describeVaultDB` races its writers from two devices, under every interleaving it can make** (`safebyok/testing` grows). A new option, `makeDevices(turnstile)`, makes devices over one fresh backend -- each an adapter of its own, sharing nothing but the backend -- and passes the `turnstile` before each round trip a device makes to it (`throughTurnstile` wires one around a client's methods). The race lines (3.1 to 3.5, 3.7 and 4.5) then run under `raceEveryWay`: the moves made together, staggered a few microtasks and ticks each way round, and each move held before every one of its round trips while the other moves; four racers for the last place each held midway, then let go together. A device that cannot finish while another waits at the turnstile fails the race: the two share a lock, a queue or a connection that real devices would not, or the adapter holds a lock from one round trip to the next. `expectRoundTripsThroughTurnstile(makeDevices)` shows an adapter's factory wires it. Without `makeDevices`, the races run through one adapter as before, under the same schedules, and their titles say so.
  
  New checks across devices: line 2.1 (a write on one device seen by the next read on another), 4.5 past the limit (a vault filled by a device allowed more), and 6.1 from another device. The push tests no longer guess that a watch is live after 50 ms: they make a write the watch hears first, and then need some call to `onChange` to read the vault as each write left it, so a push that comes too early, or not at all, fails; an unsubscribed watch is checked through several writes, not one tick. Each of these checks is also exported, runnable on its own, as `vaultDBTimingChecks`.
  
  An adapter's own tests that pass `makeDevices` see new tests; one whose devices secretly share an adapter, a backend per device, or a lock now fails them.
  
  **`postgresVaultDB` calls a subscriber once as its listen begins** (`safebyok-postgres`). A write that landed while the listen was starting was never heard, and a vault -- which subscribes, then reads -- could read the vault before that write and show it stale until the next one. Now it reads again once the watch is live. Through it, **`safebyok-graphql`'s `safebyokVaultChanged` sends one change as the subscription starts**. A host counting `onChange` calls sees one more at the start; the VaultDB contract's line 6.1 now says a watch that starts late calls once it is live. The schema's description of `safebyokVaultChanged` reads "whenever the vault may have changed".
