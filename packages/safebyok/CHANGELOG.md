- [#125](https://github.com/mrflip/safebyok/pull/125) [`161a6b1`](https://github.com/mrflip/safebyok/commit/161a6b17f9cf6d602c627712e22dc0edc453b2e0) Thanks [@mrflip](https://github.com/mrflip)! - Key derivers are checked harder, and a passkey can change a passphrase.
  
  **`KeyDeriver` is now a union** (breaking for a host's types; the reserved labels and the zeroed
  bytes below may break a host's own deriver too): `Argon2idKeyDeriver`
  (a whole `KeyDeriverSpec` beside `key_deriver_label`, `salt_bytes` and `deriveKeyBytes`: what
  `argon2idDeriver`, `argon2idWebV1Deriver` and `safebyok-fastkey`'s derivers return) or
  `CustomKeyDeriver` (those three fields, and optionally an `algorithm` of the host's naming).
  Every field keeps its name. What changes: an `Argon2idKeyDeriver` must carry every parameter
  of the spec (the union as a whole still admits a partial set, which `openVault` checks only on a
  deriver declaring `algorithm: 'argon2id'`), and a class can `implements
  CustomKeyDeriver` or `Argon2idKeyDeriver` but not `KeyDeriver` itself. `openVault` now runs
  the Argon2id spec check on any deriver declaring `algorithm: 'argon2id'`, so a spec Argon2id
  cannot run is refused at open (`bad_option`) rather than failing at the first unlock, and
  refuses a label beginning `argon2id_web_` (any case) that is not a spec safebyok supplies. A
  label beginning `test_` is warned of through the logger, not refused.
  
  * `changePassphrase(proof, newPassphrase, { unlockId? })` takes any way in as proof, a
    passkey's answer included. Given a passkey's answer on a vault of several passphrases, say
    which to replace with `unlockId` (`bad_option` otherwise). A passphrase proof behaves as before.
  * The vault zeroes the bytes a deriver hands back once imported, so a deriver must return a
    fresh array each call, and refuses (`bad_option`) bytes in a `SharedArrayBuffer`.
  * `argon2idDeriver`, `argon2idWebV1Deriver` and `argon2idWasmDeriver` refuse a salt of another
    length than the spec's (`bad_option`) before deriving. `ensureSaltFits` is exported for a
    deriver of another implementation to do the same.
  * `parseKeyDeriverSpec` now lives in the spec module and refuses the reserved labels too.
  * A `wrong_passphrase` beside passphrases made by another key deriver says how many went
    untried, and that opening the vault where it was made may help.
  * `UnlockSummary` (the snapshot's `unlocks`) gains `device_id` and `registered_at`.
  * New exports: `Argon2idKeyDeriver`, `CustomKeyDeriver`, `ensureSaltFits`.
  * `Envelope.sealPassphrase` and `sealPasskey` (internal) return the envelope alone.

- [#125](https://github.com/mrflip/safebyok/pull/125) [`80673f9`](https://github.com/mrflip/safebyok/commit/80673f9d073f592b111a9144df1a3eb26e394e6c) Thanks [@mrflip](https://github.com/mrflip)! - **Every adapter now compares a lockbox write's `vault_key_epoch`** (VAULTDB.md line 3.8): `idbVaultDB` in the write's transaction, the Convex component's `updateBox` mutation, and `postgresVaultDB` in the write's one statement, reading the vault's bundle row `FOR SHARE`; `graphqlVaultDB` gets it from the VaultDB its server serves. A lockbox write sealed under a vaultKey the bundle no longer stands for now refuses as `stale_write`, writing nothing. Every vault is at `vault_key_epoch` 1 today, so no write a host makes now is refused by it. Convex hosts redeploy the component to take it up.
  
  **Postgres: a bundle update waits for lockbox writes in flight.** The `FOR SHARE` read is a shared lock: lockbox writes never wait for each other on the bundle (two writes to one boxlabel still meet at its row, as before). A hard-cap trigger that takes `FOR UPDATE` on the vault row, as the one in 0.3.0's README did, deadlocks two first writes into one vault, one of them failing as `storage_unavailable`: what becomes of it is in this release's entry "The vocabulary reform, in one place".
  
  **`safebyok/testing`: `describeVaultDB` no longer takes `comparesVaultKeyEpoch`.** Line 3.8's tests run for every adapter; drop the option, and compare the epoch in your adapter's lockbox write.
  
  **`close()`, and a refresh that outlives the key, now stop a read in flight.** A `read()` or `use()` under way when the handle is closed hands back nothing and refuses with `vault_closed`; one under way when a refresh finds the vault's ways in changed on another device, or the vault gone, refuses with `vault_locked`. A `lockSoon()` grace running out, and a clock that cannot be read, still let a read in hand finish.
  
  **A device-store failure says what failed.** Still kind `storage_unavailable`, the device store's error its cause, but the message now names the step -- reading or writing the remembered unlock, reading or writing this device's mark of the vault, erasing either -- and what to do. `eraseDamagedVault` now reports a device-store failure the same way (it threw the device store's own error before).

- [#125](https://github.com/mrflip/safebyok/pull/125) [`e25bf68`](https://github.com/mrflip/safebyok/commit/e25bf6885b6f42cc621a3d4108c2fc007da5c79f) Thanks [@mrflip](https://github.com/mrflip)! - **Renamed: every `Ms` is now `Millis`.** `ForeverMs` is `ForeverMillis`, and a vault's `reentryWindowMs` is its `reentryWindowMillis`. Rename them where your app reads them. New exports: `MinuteMillis`, and `MaxReentryHours` (588).
  
  **The unlock window has a hard edge.** `forcePassphraseReentryHours` takes a number of hours up to 588 (24.5 days), or `Infinity` for "until `lock()`"; a finite number past 588 is now refused with `bad_option`, where it used to be clamped. From `askPassphraseAt` no new work starts, and a minute later a timer drops the vaultKey, with no call needed; a timer that runs late is caught at the next call. The timer is `unref`'d, so it never keeps a Node or Bun process alive. Compare `askPassphraseAt` (and `reentryWindowMillis`) against `FarFuture - MinuteMillis` (`ForeverMillis - MinuteMillis`) to say "until locked", never for equality.
  
  **The window renews whenever the user types a passphrase and it proves**: `changePassphrase()`, and `addPassphrase()`, `addPasskey()` or `removeUnlock()` with a passphrase as proof, start it again from then, as `unlock()` does. A passkey proving such a change keeps the deadline that stands. Reads, stores and refreshes never move it. A window that runs out while an `unlock()` or `changePassphrase()` is under way is no lock: the call ends unlocked, with a window of its own. `lockSoon()` on a key already past its deadline gets no more than the minute it had left.
  
  **A lock in one tab now defeats an unlock under way in another.** The device mark gains `lock_generation`, raised by `lock()`, `lockSoon()` and a sign-out's lock; an unlock writes its remembered record only while the mark stands where it found it. Its format moves to `safebyok-mark-v2`. For a host's own `DeviceDB`: `writeUnlock(unlock, expected)` now takes an `UnlockExpectation` and refuses with `stale_write` when the scope's mark stands at another `lock_generation`, and `writeMark` keeps the higher `lock_generation` of the mark it replaces; the `describeDeviceDB` battery in `safebyok/testing` checks both. A device mark written before this reads as none: the device starts its rollback check again from what storage holds now, once, and says so through the logger's `warn`.
  
  **`close()` is not a lock**: an unlock under way when the handle closes leaves the record it wrote, and the next open picks it up. **A device store that fails while `openVault` reads the remembered unlock** now rejects with kind `storage_unavailable`, the store's error as its cause, so `VaultProvider` shows it in `openError` with a retry, not the error boundary.

A `lock()` on a scope with no mark writes one with nothing seen, so it stops another tab's first unlock too. A mark written before this reads as none, once. A host's own `DeviceDB` stores the mark as given, as before. The new type `SeenVault` is exported.

Its next move is "update the app": never offer to erase it. A host switching exhaustively on kinds adds a case.

  **`destroy()` on a handle that has seen no vault** reads storage first, and destroys a vault that stands there. A change to the ways in that has landed in storage now resolves even when this device fails to keep its own mark or remembered unlock afterwards; the logger says so.
