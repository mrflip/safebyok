- [#256](https://github.com/mrflip/safebyok/pull/256) [`fd9f9e5`](https://github.com/mrflip/safebyok/commit/fd9f9e5bceb2a578ad068a133e7547fcb40ec4ab) Thanks [@mrflip](https://github.com/mrflip)! - **`putBox` takes the box first and the whisper second, and either may be left out: `vault.putBox({ boxlabel, sidecar? }, whisper?)`.** It resolves the `Box` as stored. Given both the sidecar and the whisper, it reads nothing and writes over the revision the snapshot lists (keeping its `registered_at`), or as a new box when none is listed; a listing a moment stale refuses `stale_write`. Leave either out to keep the box's own: it reads the box, opens it, and writes over the revision it read; leaving out the whisper where no box stands refuses the new kind **`no_whisper`**, at once and asking nobody for a box a locked vault's listing does not show. `putBox('label', whisper, { sidecar })` is gone: write `putBox({ boxlabel: 'label', sidecar }, whisper)`. **`getBox()` resolves null for a box that is not there** (it refused `absent_box`); `getWhisper()`, `useWhisper()` and `delBox()` still refuse `absent_box`. **`delBox()` resolves what it removed**, `{ boxlabel, vault_tok, outcome: 'deleted' | 'deleted_other' }` (the exported `DeletedBox`). **`vault.decryptWhisper(box)` is gone: a `Box` opens itself with `box.extractWhisper()`** (and `tryExtractWhisper()`), under the vault's lease, which stays the Vault object's own; a `Lease` hands out no record (its `record` getter is gone), and nothing reachable from a Vault object yields a lease, a key or a wrapped key. **`vault.tryDemandConsistentWith` is gone**: `vault.consistentWith(thing, { leaseBound? })` asks the demand's question as a boolean, refusing nothing and dropping no lease, beside `demandConsistentWith`, which throws. A `Box` carries the whole stamp of the vault it was made under (`applabel`, `user_id`, `vaultlabel`, `vault_tok`, `vault_epoch`, `gate_epoch`), shown in `{ ...box }` and its JSON, and refuses `vault_gone`, `vault_remade` or `gate_moved` once the vault moves on; a box sealed and not yet stored names the revision it was sealed over as `box.baseRevisionTok`. `Box.seal(vault, { boxlabel, sidecar?, base? }, whisper)` (with `Box.trySeal`) seals under the vault's lease; `box.tryOpen` and `box.open` are gone. **A `Lease` no longer holds the vaultKey unwrapped**: `lease.cipheredWith(bytes, visible)`, `lease.decipherWith(ciphered, visible)` and `lease.sealProps(visible, { whisper })` (each with its `try` form) unwrap it for that one call; `Lease.grant`, `lease.tryOpen`, `wrapBoxKey` and `unwrapBoxKey` are gone. A lease this device keeps is taken up as read, and one whose wrap will not open refuses its first use with the new kind **`damaged_lease`** (bad news), erasing it and locking the vault, where it was discarded at the hello with a warning. A lock landing while a `putBox()` seals its whisper now refuses `vault_locked`, writing nothing; one landing while `getBox()` reads lets the box through, as it holds nothing secret. **`VaultDB.getBox(scope, boxlabel, expected)` takes the `vault_tok` its reader holds** (`BoxGetExpectation`) and refuses `vault_mismatch`, reading the vault props and the box in one step, where that vault no longer stands; every adapter does so (the Convex component's `getBox` query answers `{ read, box_stored }` or `{ read: false, refusalkind }`, the GraphQL `safebyokGetBox` field takes `expected`, Postgres reads both in one statement). A vault's box read that meets it refuses **`vault_gone`** (a box of a vault made anew elsewhere was `damaged_box`), and the next `hello()` reads storage afresh. **Vaults stored before** read as they did: nothing stored changes shape. A host whose own VaultDB adapter implements `doGetBox` must take the new `expected` argument and compare it in the same step as the read.

## 0.4.0

### Minor Changes

- [#125](https://github.com/mrflip/safebyok/pull/125) [`161a6b1`](https://github.com/mrflip/safebyok/commit/161a6b17f9cf6d602c627712e22dc0edc453b2e0) Thanks [@mrflip](https://github.com/mrflip)! - Key derivers are checked harder, and a passkey can change a passphrase.
  
  **`KeyDeriver` is now a union** (breaking for a host's types; the reserved labels and the zeroed
  bytes below may break a host's own deriver too): `Argon2idKeyDeriver`
  (a whole `KeyDeriverSpec` beside `key_deriver_label`, `salt_bytes` and `deriveKeyBytes`: what
  `argon2idDeriver`, `argon2idWebV1Deriver` and `safebyok-fastkey`'s derivers return) or
  `CustomKeyDeriver` (those three fields, and optionally an `algorithm` of the host's naming).
  Every field keeps its name. What changes: an `Argon2idKeyDeriver` must carry every parameter
  of the spec (the union as a whole still admits a partial set, which `openVault` checks only on a
  deriver declaring `algorithm: 'argon2id'`), and a class can `implements
  CustomKeyDeriver` or `Argon2idKeyDeriver` but not `KeyDeriver` itself. `openVault` now runs
  the Argon2id spec check on any deriver declaring `algorithm: 'argon2id'`, so a spec Argon2id
  cannot run is refused at open (`bad_option`) rather than failing at the first unlock, and
  refuses a label beginning `argon2id_web_` (any case) that is not a spec safebyok supplies. A
  label beginning `test_` is warned of through the logger, not refused.
  
  * `changePassphrase(proof, newPassphrase, { unlockId? })` takes any way in as proof, a
    passkey's answer included. Given a passkey's answer on a vault of several passphrases, say
    which to replace with `unlockId` (`bad_option` otherwise). A passphrase proof behaves as before.
  * The vault zeroes the bytes a deriver hands back once imported, so a deriver must return a
    fresh array each call, and refuses (`bad_option`) bytes in a `SharedArrayBuffer`.
  * `argon2idDeriver`, `argon2idWebV1Deriver` and `argon2idWasmDeriver` refuse a salt of another
    length than the spec's (`bad_option`) before deriving. `ensureSaltFits` is exported for a
    deriver of another implementation to do the same.
  * `parseKeyDeriverSpec` now lives in the spec module and refuses the reserved labels too.
  * A `wrong_passphrase` beside passphrases made by another key deriver says how many went
    untried, and that opening the vault where it was made may help.
  * `UnlockSummary` (the snapshot's `unlocks`) gains `device_id` and `registered_at`.
  * New exports: `Argon2idKeyDeriver`, `CustomKeyDeriver`, `ensureSaltFits`.
  * `Envelope.sealPassphrase` and `sealPasskey` (internal) return the envelope alone.

- [#158](https://github.com/mrflip/safebyok/pull/158) [`c644000`](https://github.com/mrflip/safebyok/commit/c6440005f6e503d13dd99f6a62764671929d976e) Thanks [@mrflip](https://github.com/mrflip)! - A vault is made, then says hello. openVault(opts) is gone, with no alias: Vault.make(opts) makes the handle at once, synchronously, throwing misuse (bad_label, bad_option, insecure_context) before storage is touched, and starts vault.hello() itself, which reads the vault props and this device's lease and settles the snapshot from opening into absent, locked or unlocked. Where a host wrote `const vault = await openVault(opts)`, it writes `const vault = Vault.make(opts)`, and `await vault.hello()` where it wants to know the vault has settled or why it could not; every call but lock(), lockSoon() and close() waits for hello first, so a call made before storage answered simply waits. OpenVaultOpts is MakeVaultOpts, and Vault is now a value as well as the handle's type. A hello refused no longer leaves nothing behind: the handle stands, its storage watch live, and the snapshot's new field trouble (a VaultError, or null) says why, the state still opening; the vault's logger warns of it ({ call: 'hello' }, where the logger's story said 'openVault'; Vault.make's own notices say 'make'), and calling hello() again, or any other call, tries again. Close the handle to let it go. Once settled, a later hello() reads nothing anew, until a read of storage fails (trouble then says why, cleared by the next read that succeeds), storage the vault cannot trust refuses it (identity_revoked, rolled_back, newer_format), or the vault is retired: its next call then reads storage and the lease afresh, so after such a refusal the next call meets it again rather than vault_locked. A lock() or lockSoon() made while a hello is taking up the lease wins over it. Vault.make refuses an option it does not take as bad_option, naming it, and naming the new name of a retired one (forcePassphraseReentryHours is leaseHours): it used to ignore it, so a retired lease setting quietly gave the seven-day default. React: VaultProvider makes the vault with Vault.make and hands the handle down at once, its snapshot opening until hello settles, where vault used to stay null until the open succeeded; openError is the snapshot's trouble while the vault is still opening, when it is a condition; retryOpen() and retireDamagedVault() have the same handle say hello again rather than open a new one; and a prop Vault.make does not take is thrown to the error boundary as bad_option, where the provider used to drop it. safebyok/testing gains settledVault(opts), Vault.make then hello.

- [#158](https://github.com/mrflip/safebyok/pull/158) [`6f0382c`](https://github.com/mrflip/safebyok/commit/6f0382c52bf04e7ff83b1789787ab89c8cc10877) Thanks [@mrflip](https://github.com/mrflip)! - The vocabulary reform, in one place: this release renames what a host touches, and what a vault stores, to the words VOCABULARY.md defines. Nothing has a compatibility alias, and nothing stored before it is read. This release's other entries say each change in full; this is what a host does.
  
  Names. The unlock envelope is the wayin; what a device keeps to unlock again is the lease (`forcePassphraseReentryHours` is `leaseHours`); a lockbox's public bag is its sidecar; the bundle is the vault props; erase is retire (`store`, `read`, `use`, `erase` and `destroy` are `storeBox`, `readBox`, `useBox`, `retireBox` and `retire`); `revision_id` is `revision_tok`; the encryption's "binding" is its ctx. Every renamed export, option, stored field, ckey and refusal kind (`absent_wayin`, `damaged_wayin`, `last_wayin`, `too_many_wayins`, `damaged_vault`) is in `notes/old_vocabulary.md`, beside its replacement; a DeviceDB or VaultDB of your own renames its methods to match.
  
  Making a vault. `openVault(opts)` is gone, with no alias: write `const vault = Vault.make(opts)`, which returns at once, and `await vault.hello()` where you want to know the vault has settled. `Vault.make` now refuses an option it does not take as `bad_option`, naming it (and the new name of a retired one), where it used to ignore it; VaultProvider throws a prop it does not take to its error boundary the same way. A hello that cannot read storage leaves the vault `opening` with the snapshot's new `trouble` saying why, and any later call tries again.
  
  Behaviour. `storeBox()` no longer retries when another device wrote first: it catches up once and throws `stale_write` at once, for your app to decide whether to store again. A first unlock that loses the race to another device creating the vault throws the new `created_elsewhere` in place of `wrong_passphrase`: a host that says "check for typos" on `wrong_passphrase` should handle it too (safebyok-react's PassphraseModal shows it as advice).
  
  Stored formats. A host upgrading from 0.3.0 has vault props in `safebyok-vault-v2`, lockboxes in `safebyok-lockbox-v2` and a lease in `safebyok-unlock-v1`; this release writes `safebyok-vault-v3`, `safebyok-lockbox-v5` and `safebyok-lease-v1`. There is no migration, and an old record fails safe. Where an old vault's record is still found, in a VaultDB of your own, it reads as damaged (`damaged_vault`) and is retired with `retireDamagedVault()` and made afresh, and any older lockbox lists as damaged and is stored again or retired (its whisper stored again by the user). In Postgres, whose tables you drop (below), a vault written before reads as absent, and the user makes it again. So it does in `localVaultDB` and `idbVaultDB`, which 0.3.0 filed under JSON-tuple ckeys (`["vault","acme","u1","main"]`) where this release joins them on `^` (`vault^acme^u1^main`), its old rows left as they were. On the device an old lease is never read: `idbDeviceDB` deletes 0.3.0's rows, the device mark's with the lease's, unread, and a DeviceDB of your own that hands an old lease back sees the vault erase it, with one warning to the logger. Either way each device asks for the passphrase or passkey once.
  
  Postgres. There is no migration before 1.0: a database made by `safebyok-postgres@0.3.0`, or from `main` between releases, drops the package's tables and lets this release make them afresh. **This deletes every vault and lockbox stored in Postgres**: each user makes their vault again and stores their whispers anew. This replaces every Postgres step in this release's other entries. Run once, before this release's `VaultTablesSql` first runs, and with no server on the old version still running (one that runs its `VaultTablesSql` as it starts would make the old tables again):
  
  ```sql
  DROP TABLE IF EXISTS safebyok_lockboxes, safebyok_vaults, safebyok_bundles;
  DROP FUNCTION IF EXISTS safebyok_vault_changed(), safebyok_lockboxes_capped();  -- the notify trigger's, and the hard cap's from 0.3.0's README
  ```
  
  Then run this release's `VaultTablesSql`, and `VaultNotifySql` if you use push. (Drop first: `VaultTablesSql` never changes a table already there, so an old one would stand in place of the new.) Nothing readable is lost: kept, every lockbox written before this release would list as damaged, and every vault read as `damaged_vault`; dropped, each vault reads as absent. The second `DROP` removes `safebyok_lockboxes_capped`, the hard-cap function 0.3.0's README gave, which names the old tables: a hard cap of your own is yours to write again against the new tables, if you want one, and the README gives a prompt for that.
  
  Convex. The component's tables and validators changed (`safebyok_vaults`, `wayins`, `sidecar_json`, `revision_tok`, `vault_row_id`), so a deployment holding rows written before this no longer matches the component's schema: clear the component's tables before deploying it, and regenerate your app's `api`.
  
  GraphQL. The schema's types and operations follow (`SafebyokVaultProps`, `SafebyokWayin`, `safebyokReadVaultProps`, `safebyokRetireBox` and the rest): serve the new schema and the new client together.

- [#79](https://github.com/mrflip/safebyok/pull/79) [`19fb0bb`](https://github.com/mrflip/safebyok/commit/19fb0bbbba2f80f589181cb5ed2440733d07b8f3) Thanks [@mrflip](https://github.com/mrflip)! - New package, `safebyok-fastkey`: Argon2id through WebAssembly (`hash-wasm`) as a safebyok KeyDeriver, about four times faster than the core's `@noble/hashes` deriver and deriving the same bytes. `argon2idWasmWebV1Deriver` stands in for `argon2idWebV1Deriver` under the same `argon2id_web_v1` label, so a vault made under either opens under the other; `argon2idWasmDeriver(spec)` runs a spec of the host's own.   The core exports `parseKeyDeriverSpec(spec)`, the check `argon2idDeriver` makes of a spec, for a deriver over another Argon2id implementation to make the same. Its refusal now begins "Argon2id cannot run that keyDeriverSpec" where it named `argon2idDeriver`. Nothing stored changes.
