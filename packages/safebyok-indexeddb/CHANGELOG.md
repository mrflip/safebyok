A hard-cap trigger that takes `FOR UPDATE` on the vault row, as the one in 0.3.0's README did, deadlocks two first writes into one vault, one of them failing as `storage_unavailable`: what becomes of it is in this release's entry "The vocabulary reform, in one place".

  **A device-store failure says what failed.** Still kind `storage_unavailable`, the device store's error its cause, but the message now names the step -- reading or writing the remembered unlock, reading or writing this device's mark of the vault, erasing either -- and what to do. `eraseDamagedVault` now reports a device-store failure the same way (it threw the device store's own error before).

Each verb holds every name to the floor and to a fact every adapter now declares, `maxNameBytes` (VAULTDB.md 7.3): an adapter of your own adds it. ## 0.3.0

### Minor Changes

- [#79](https://github.com/mrflip/safebyok/pull/79) [`648b2c4`](https://github.com/mrflip/safebyok/commit/648b2c4fe365bf40bb115b34c57b1d5976524431) Thanks [@mrflip](https://github.com/mrflip)! - **`passphrase_epoch` is now `unlock_epoch`, in every stored record and every adapter, with no alias and no migration.** The counter moves whenever any way into the vault changes (a passphrase or a passkey added, removed or changed), so the old name no longer fit. It is renamed in the vault bundle (`VaultBundle`), the remembered device unlock (`DeviceUnlock`), a `VaultDB`'s `BundleExpectation`, `safebyok/testing`'s `bundleOf`, `safebyok-convex`'s tables and validators, `safebyok-indexeddb`'s checks, `safebyok-postgres`'s column (`vault-tables.sql` and the exported DDL), and `safebyok-graphql`'s schema fields. What a host with vaults already stored will see, by store:
  
  * **IndexedDB, `localVaultDB`, or a host's own `VaultDB`**: a bundle written under the old name fails validation and reads as `corrupt_record`, left as it is: a development vault is cleared from storage and made anew.
  * **Postgres**: `vault-tables.sql` creates only the tables that are missing, so running it again leaves an existing `safebyok_bundles` with its old column, and every bundle read and write fails as `storage_unavailable`, so no vault opens, until the host renames it, `ALTER TABLE safebyok_bundles RENAME COLUMN passphrase_epoch TO unlock_epoch` (which keeps every vault readable), or drops and re-creates the table.
  * **Convex**: a deployment holding bundle rows under the old name refuses the new component schema at deploy until those rows (and their vaults' lockboxes) are deleted.
  * **GraphQL**: the client and server halves must be the same version; a client of one against a server of the other fails every vault call as `storage_unavailable`.
  
  On every device, a remembered unlock written under the old name reads as absent, so that device asks for the passphrase once.

- [#79](https://github.com/mrflip/safebyok/pull/79) [`d6d278a`](https://github.com/mrflip/safebyok/commit/d6d278a939454b4139c91456ba3e54a263e7922e) Thanks [@mrflip](https://github.com/mrflip)! - **The IndexedDB vault store is a package of its own, `safebyok-indexeddb`; `safebyok/idb` keeps the device store.** A host using `idbVaultDB` changes one import, `from 'safebyok/idb'` to `from 'safebyok-indexeddb'`, and adds the package: its vaults read on unchanged, from the same IndexedDB database, rows and ckeys. `safebyok/idb` no longer exports `idbVaultDB` (no re-export is kept), and its `inspectIdb({ dbName, shelf })` becomes two windows, one beside each store: `inspectIdbDeviceDB({ dbName })` in `safebyok/idb`, and `inspectIdbVaultDB({ dbName })` in `safebyok-indexeddb`; the `IdbShelf` type is gone. Every verb of the new `idbVaultDB` is one IndexedDB transaction, where the old one read and wrote in two: a write racing another tab's now lands only while what it expects still stands, and is refused `stale_write` otherwise, two tabs creating a vault at once settle on one, and erasing a vault removes its every lockbox or none. A write now also tells other tabs over the BroadcastChannel when nothing in its own tab is listening, and a subscriber that throws no longer turns a write that landed into a refusal. Its README is the template for a key-value storage adapter of your own.

- [#79](https://github.com/mrflip/safebyok/pull/79) [`53b1f1a`](https://github.com/mrflip/safebyok/commit/53b1f1aabea16102dc7bfb6187410369e05b2e53) Thanks [@mrflip](https://github.com/mrflip)! - **Every storage adapter declares how many lockboxes it holds in one vault, and the Postgres server enforces its own.**
  
  * **Breaking, for adapter authors:** `VaultDB` gains an abstract `maxLockboxes`, the most lockboxes the backend holds in one vault, or `Infinity` for no limit. A custom adapter adds `readonly maxLockboxes = Infinity`, or its backend's real limit (a large whole number where the limit must cross a wire or be stored). `openVault` refuses, with kind `bad_option`, an adapter that declares none.
  * `openVault`'s `maxLockboxes` defaults to the smaller of `MaxLockboxes` (100) and the adapter's own, and is refused with kind `bad_option` when it is larger than the adapter's.
  * `localVaultDB` and `idbVaultDB` declare `Infinity`; `convexVaultDB` declares the component's own limit, 8,000.
  * `postgresVaultDB` takes a `maxLockboxes` option (default 1000; for no practical limit pass a large number, such as `1_200_300_400_500_600`, since `Infinity` cannot reach Postgres) and enforces it, as a best effort, inside the statement that inserts a new lockbox, refusing one past it with kind `vault_full`; a replacement never is. Writers racing for the last places may each find room and all land, a few past the limit, which the VaultDB contract allows. It keeps no count in the tables: `safebyok_bundles` has no `lockbox_count` column and nothing counts lockboxes by trigger.
  * `graphqlVaultDB(client, { maxLockboxes })` declares what the server's VaultDB enforces (default 1000, the Postgres VaultDB's default); the server's `vault_full` crosses as itself.

- [#90](https://github.com/mrflip/safebyok/pull/90) [`4988661`](https://github.com/mrflip/safebyok/commit/49886618f5fed0cdd41d00992bb0897dcdccf014) Thanks [@mrflip](https://github.com/mrflip)! - **The stored format changes, with no migration** (until 1.0.0, nothing binds backward). `localVaultDB`, safebyok-indexeddb's `idbVaultDB`, `idbDeviceDB` and `memoryDeviceDB` now file each row under the JSON text of its kind and names -- `["vault","acme","u1","main"]`, `["box","acme","u1","main","anthropic"]`, `["unlock","acme","u1","main"]` -- in place of the colon-joined `vault:acme:u1:main`. JSON quotes every name, so a name may hold any text, colons included, without two vaults ever sharing a row or listing each other's lockboxes.
  
  What a host will see: a vault stored by an earlier version under one of these adapters reads as absent, so `openVault` reports it `absent` and the next `unlock()` makes a new, empty vault; a remembered unlock reads as absent, so the user enters the passphrase again. Old vault rows are not read, moved or deleted; they hold only ciphertext, and a host that wants them gone wipes the vault shelf once (`inspectIdbVaultDB({ dbName }).wipe()` from safebyok-indexeddb, or the `localStorage` prefix it gave `domStore`). An old remembered unlock on the device is different, since it keeps the vaultKey wrapped under this browser's localUnlockKey: `idbDeviceDB` deletes it, unread, the first time it reads or erases a remembered unlock after the upgrade -- an open that finds the vault, or any lock; under `idbVaultDB` or `localVaultDB`, whose first open finds no vault, that is the first lock or the first open after an unlock -- along with any other row on the device shelf that is not under an unlock's new ckey, so `lock()` still forgets every unlock on the device. `idbDeviceDB({ dbName }).eraseAll()` now clears the whole device shelf. The Convex adapter keeps its names in columns and is unaffected.
  
  New export: `Ckeys`, the ckeys these adapters use (`bundle`, `box`, `unlock`, `boxPrefix`, `isBoxIn`, `isUnlock`), for an adapter of your own over a key-value store.

### Patch Changes

- [#79](https://github.com/mrflip/safebyok/pull/79) [`9e4a6bd`](https://github.com/mrflip/safebyok/commit/9e4a6bdaa519eee2a0e7f504c1330657662f7fd8) Thanks [@mrflip](https://github.com/mrflip)! - `safebyok-indexeddb`'s BroadcastChannel no longer holds a Node or Bun process open (it is `unref`ed where the platform's channel has `unref`), and a `subscribe` listener that throws no longer escapes as an uncaught error, which ended a Node process: what it threw is dropped, and the other listeners are still called.

- [#115](https://github.com/mrflip/safebyok/pull/115) [`771f841`](https://github.com/mrflip/safebyok/commit/771f8417336c3067cba38e4913d06a395972d17a) Thanks [@mrflip](https://github.com/mrflip)! - **A vault stored damaged can now be erased, to start over.** When the stored bundle fails its checks `openVault` refuses with `damaged_bundle`, and `destroy()` needs a handle that was never made. New: `eraseDamagedVault(opts)`, taking `openVault`'s options, erases that vault's bundle and lockboxes through the `VaultDB` and the unlock this device remembers through the `DeviceDB`. It erases a vault `openVault` refuses as `damaged_bundle` and no other: a sound vault is refused with `bad_option` and nothing erased (it is `destroy()`'s), and a record too damaged to show its `vault_id`, or one a newer safebyok may have written (a `format`, unlock method or number of unlocks this one does not know), is refused as `damaged_bundle`, nothing erased. Any change to what a stored record may hold -- a field, a shape, or a range a check accepts -- must bump `format` for that to hold.
  
  - **`safebyok`**: exports `eraseDamagedVault` and its `EraseDamagedVaultOpts`, and the `VaultDB` base class gains a public verb, `eraseDamagedVault(scope, validators?)`, which adapters inherit and implement nothing for. An adapter that hands each call on to another `VaultDB`'s public verbs hands this one on too. `localVaultDB` now erases a whole vault on its `vault_id` alone, as `VAULTDB.md` line 3.5 says; it also required a readable `unlock_epoch`, which kept a damaged vault from being erased.
  - **`safebyok-react`**: `useVault()` gains `eraseDamagedVault()`, which erases the vault `openError` reports as `damaged_bundle` with the provider's own options and opens again; it does nothing for any other `openError`, and opens again when the erase finds the vault sound or made anew.
  - **`safebyok-indexeddb`**: `idbVaultDB` erases a whole vault on its `vault_id` alone, likewise.

- [#115](https://github.com/mrflip/safebyok/pull/115) [`66a1095`](https://github.com/mrflip/safebyok/commit/66a1095a5e78e8da220e9f436039eb16b6b2bf00) Thanks [@mrflip](https://github.com/mrflip)! - **`idbVaultDB` reads only the vault's own rows.** Listing a vault's lockboxes, and erasing a vault, used to read every row on the shelf, every user's and vault's, and filter them in memory; both now work on the key range under the vault's lockbox prefix, so their cost follows the vault, not the database. What is stored is unchanged.
  
  **A write IndexedDB fails no longer carries a null cause.** When a request in a write fails, the `storage_unavailable` refusal's `cause` is now the error that request failed with (a `ConstraintError`, an `AbortError`), where it used to be the transaction's error, still `null` at that moment; when the browser gives no error at all, it is an Error reading "The IndexedDB request failed for an unknown reason", never `null`.
  
  **The change bell closes its BroadcastChannel when it is done with it.** The channel closes when the last listener of a database leaves (a vault's `close()`), and a write that finds no listener in the tab opens one only to tell the other tabs; it is opened afresh when next needed. It was kept open for the life of the page.
