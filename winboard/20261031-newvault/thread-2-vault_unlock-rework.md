# Thread 2: vault_unlock, the rework (2026-10-31)

For whoever works on `models/vault.ts`'s *Unlocking* or `models/lease.ts` next: what the review's rework changed, and the approaches set aside.

The orchestrator's directives after the review on PR #412 (YOLO):

* *DeviceDB put side*: `putLease`/`tryPutLease<RowT extends KeptLeaseRow>(record: RowT)` resolve the row typed as handed, so the old core's `tryPutLease` of a `LeaseRecord` still types as before; `doPutLease` takes a `KeptLeaseRow` (idb.ts's override, typed `LeaseRecord`, compiles by method bivariance and was left, being outside the thread's files). `keptLeaseRow`'s models branch now names `applabel`, `user_id`, `vaultlabel`, which `Scopepath.lease(record)` needs; a 7001 row without them reads absent. A plain `KeptLeaseRow` return was tried first and broke src/vault.ts's tool type: the generic is the smallest fix. A test unlocks through `memoryDeviceDB()` and takes the kept lease up in `anotherSession()`.
* *`Lease.letGo()`* (not `release()`: in lease vocabulary releasing hands the lease back, which is `forget()`'s erase, and tests already use `release()` for gates): drops the record and disposes the autolock, erasing nothing. `forget()` calls it, then erases. `isForgotten` reads true for a let-go lease too (name left).
* *The look*: `takeUpKeptLease()` looks whenever `#lease` is null; `#keptLookup` is only the in-flight join, cleared in the look's own `finally` (its first statement awaits `#leaseChores`, so it never clears before it is set). A declined kept lease (not in force, or one in force arrived meanwhile) is let go.
* *The join*: `#unlock` first joins `#unlocking` where an unlock by proof is in flight, then looks, then `this.#unlocking ??= this.#unlockAlone(closure)`. A call without a closure joins one in flight and refuses only where none is, so a closure-less `ensureUnlocked()` racing one with a proof does not make the proof's caller refuse. Rejected: `#unlocking ??= this.#unlock(closure)` around the whole unlock (the Trigger idiom literally), because a closure-less first caller would make a concurrent caller with a proof refuse `vault_locked`. `#unlockAlone` is a separate try/finally around `#unlockByProof` because a synchronous throw before the first await (the `gate` getter) would run the finally before the `??=` assigns, leaving a rejected `#unlocking` forever; `.finally()` chaining is refused by `unicorn/prefer-await`.
* *`#setLease`* lets a displaced lease go, so its autolock no longer locks the vault and erases the new lease's record at the old `autolock_at`; `takeUpLease` goes through it.
* *`goodbye`* calls `vault.letLeaseGo()`: the vault reads locked, its lease is let go, the kept record stays. `lock()` still erases.
* *`takeUpLease`* refuses 'bad_option' (`LeaseOfOtherHolder`, its sentence widened) a lease whose holder is another Vault object or whose stamp is another vault's, and 'vault_locked' (`LeaseNotInForce`) one not in force. The holder check was kept beside the stamp check: a lease's autolock locks the Vault object it was granted, so a lease of the same vault held by another Vault object is still refused. For every Lease the models make, the holder check implies the stamp check.
* Tests (19 in vault-unlock.test.ts): the join (closure once under three concurrent `ensureUnlocked`, one without a closure), the displaced lease's timer (fake `setTimeout`, past the old `autolock_at`, no erase, vault unlocked), goodbye leaving the kept record for the next session, the re-look taking up another session's lease, both `takeUpLease` refusals, memoryDeviceDB end to end. Removing the let-go or the join fails the matching test (checked by mutation).
* Spec: the thread-2 status line under *Vault* rewritten for the look, the join, `takeUpLease`, the let-go and goodbye.
