# Thread 4: unlock_urgent (2026-11-22)

Branch `20261122-unlock_urgent`, PR #821, stacked on #820 (on #818 and #817). Proved: `pnpm justify` green at the tip (safebyok-react-lean 271 tests in 17 files, safebyok 1399, safebyok-big 2946, safebyok-react 277, e2e 576, demos 99 + 24 + 26, scripts 331, the adapters all passing). The new regression tests failed before their changes: the unlock-form pair with Unlock stuck "Unlocking…" and disabled, the draft-in-form test with the draft still Dirty after the reset.

So a host may use React 19 Actions freely beside the kit and `useDraft`: two changes in `packages/safebyok-react-lean`, each its own commit with its test.

* **Built**:
  * **Change 1** (`src/kit/unlock-form.tsx`, `src/kit/passkey-forms.tsx`, `src/parts/passphrase-input.tsx`). `UnlockForm` and `PasskeyUnlockButton` submit from `onSubmit` (`preventDefault`, then `formActionOf(...)(new FormData(formEl))`), never `action=`, and show pending from a local `useState` (`isUnlocking`) set in the handler and cleared in `finally`. Their submit is a plain `<button type="submit" disabled={isUnlocking}>`, no longer the parts' `SubmitButton` (which reads `useFormStatus`). `UnlockForm` calls `formEl.reset()` in `finally`, which is what React's own form reset does, so the passphrase field empties on every submit, refused or not, at the same moment as before (after the unlock settles). `PassphraseInput` gains `isPending?: boolean`, OR'd with `useFormStatus().pending` into `useRevealToggle`. `UnlockDialog`'s doc block gains a line: the waiting call may run inside a transition or form Action.
  * **Change 2** (`src/giver/use-draft.ts`). A `useEffect` with no dependency list listens for `reset` on each form the draft's inputs belong to (`formsOf`), calling `discard`. A host writes nothing. Inputs in no form get no listener, so behave as before. The hook's doc block says a draft may sit in a form whose action calls `put`, and what a refused put there does to typed text.
  * **Tests**: `tests/kit/unlock-form.test.tsx`, a host whose Action awaits `withWhisper`, both as `startTransition(async …)` and as a `useActionState` form Action, beside `UnlockDialog`: wrong passphrase, alert, Unlock enabled again, right passphrase, the Action resolves with the key. Both failed before (button stuck "Unlocking…", disabled). The pending test now also presses Show first (field hidden while unlocking) and presses the disabled button again (one derive). `tests/parts/passphrase-input.test.tsx`: `isPending` hides a shown field. `tests/giver/use-draft.test.tsx`: the editor, with `isInForm`, is a `<form action>` driven by `useActionState`. A put refused by a dismissed unlock leaves the field empty and the draft clean, and a second Save keeps the stored key (failed before: the draft stayed Dirty). A draft outside any form keeps its typed text when another form on the page is reset.
* **Decisions made**:
  * **Pending from local state, not `unlock.isPending`.** TanStack notifies its observers through `notifyManager`, a timer tick after `mutate`, and the passkey ceremony runs before `mutate` at all. A `useState` set in the submit handler flushes before the next task, as `useFormStatus` did, so a double press still submits once, and it covers the passkey prompt. It is urgent state either way, which is what the fix needs.
  * **A plain `<button>` in the two forms**, so `SubmitButton` gets no new prop. `PassphraseInput` needed one, since its reveal state is internal and only a prop or the form status reaches it. Remounting it with a `key` would drop the field from the page during the submit, which a password manager might read.
  * **The draft listens from an effect, not from its inputs' ref callbacks.** I tried both. React 19.3 detaches a changed ref callback in the mutation phase, then resets forms at the end of that phase, then reattaches refs in the layout phase. `whisperField` hands a new ref arrow each render, so when the host renders again in the commit that resets the form (any `useActionState` host does), a listener added by the ref is gone at the moment of the reset. Probed: the ref route fails the new draft test when the editor uses `useActionState`, and the effect route passes. A passive effect's listener stays attached across the commit. It is the previous render's `discard` that runs, which is safe: `discard` touches only setters, the inputs ref and `reveal.mask` (a setter).
* **Deviations**:
  * Pending from local state, not from `unlock.isPending` as the handoff said (above).
  * A throw from `formActionOf` in these two forms (a gating at the wrong stage, or passkey options the host got wrong, which `heardCeremony` rethrows) used to reach the nearest error boundary through the form action. It is now an unhandled rejection from an event handler, as with any React event handler.
  * A form with no action whose `reset()` something calls (a `<button type="reset">`, a host's `form.reset()`) now discards the draft too. Before, that reset emptied the inputs and left the draft counting them as typed into: the same bug.
* **Discoveries**: React commits no transition's update while another is pending, so any library UI that a pending Action awaits has to run on urgent state. `useFormStatus` is transition state. The other four kit forms are left as form Actions, since nothing awaits them.
* **For the Coach**: the new `PassphraseInput` prop `isPending` (a part's surface). The two unlock forms no longer use `SubmitButton`.
