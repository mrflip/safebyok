## Rework after review: the Coach's rulings, 2026-11-22

## Second rework: the Coach's ruling, 2026-11-22, a write over a live bank keeps its lifetok

* **Why**: the lifetok is in the bank's stamp, so a revision that changed it would disable the bank (every unwrap and unseal fails). The store refuses it.
* **Core**: `demandLifetokKept(ask, raw)` in thing-classifier.ts's *Steps*, beside `demandBornAtKept`: for a bank write (put or del) over a live bank whose lifetok differs, it throws `Throwers.lifetokNotStored(stored)`, `bad_record` with `PoliciedMeta` (act `policied`) and the stored bank as `rows.dbhas`, phrase `Phrases.LifetokNotStored`. It checks its own applicability (bank only, stored `am: 'a'`), as `demandPolicies` does, so `classifyWriteThing` calls it under every write act, not only `replaced`: a del is `deleted`, and a write over a tombstone or none (`born`, `reborn`) finds no live bank and passes. The `do*` head comment in adapter-vault-db.ts names it in the check list and in the verdict order (born_at, lifetok, policies).
* **safebyok-postgres**: `WriteFunctionSpec` gains `lifetoked` (true for the bank alone, as `policied` is for the gate). The check is `(stored.am <> 'a') OR (stored.lifetok = proposed.lifetok)`, in the UPDATE's WHERE and, under COALESCE, in the read-back that reports `lifetok_ok`. It differs from the born_at check (`stored.am <> proposed.am OR ...`) on purpose: born_at is checked only live over live, the lifetok also on a del. The adapter calls `demandLifetokKept` where `lifetok_ok === false`, after the born_at verdict. A test past the adapter shows the function reports `lifetok_ok: false`.
* **Battery** (vaultdb-battery-writes.ts, *tryWriteThing(ask), the bank*): a put and a del keeping the lifetok pass (`replaced`, `deleted`); a put and a del with `OtherLifetok` (new in models-world.ts) refuse `bad_record`, `policied`, dbhas the stored bank, and leave it stored; a rebirth over the bank's tombstone with another lifetok passes (`reborn`). With the classifier's call commented out, the two refusal cases fail on MemoryVaultDB.
* **Docs**: the `Lifetok` doc (primitives.ts), the field doc (shapes-thing.ts), VOCABULARY's lifetok entry, the bank table's SQL comment and both changesets now say a vaultDB refuses a write over the live bank that changes it, and that the tombstone keeps it.
* **Discovery, fixed in docs**: Postgres will not change a function's result in place (`CREATE OR REPLACE` refuses "cannot change return type of existing function", checked on PGlite). The bank write function gains `lifetok_ok` under its old name, so the naming rule at the head of vault-functions.ts now says a host drops each function whose arguments or result changed before re-running `VaultFunctionsSql`, and the safebyok-postgres changeset names the `DROP FUNCTION` for the bank's. No vault function has been published yet (the CHANGELOG has none), so this bites only a database that ran an earlier build.
* **Set aside**: a generalized "fields a live Thing keeps" check folding born_at and lifetok together (the directive asked for one plain function and one thrower); calling the check only under `replaced` (it would miss the del); and, first, reading the stored bank whole with `BankChecks.stored` (replaced in the third rework, below).
* **Not done**: no `notes/security.md` line; this is a store integrity check, not a change to what is bound or where secret material lives.


## Third rework: the Coach's ruling, 2026-11-22, the lifetok check reads only what it compares

* **Why**: `demandLifetokKept` read the stored bank whole, so a bank damaged outside the lifetok (an extra field) made every bank write refuse `damaged_row`, even a rebirth over a damaged tombstone, while safebyok-postgres compares the lifetok in SQL and writes over it.
* **Change**: `PerKindChecks.storedLifetok` (shapes-thing.ts, beside `storedWayins`) is `obj({ lifetok })`, with the bank's own lifetok check; `BankChecks.storedLifetok` exposes it. `demandLifetokKept` returns for a non-bank, and for none or a tombstone (`storedCitedOf(ask, raw)?.am !== 'a'`, the cited part every write already reads), and only over a live bank parses the raw row with the pick (`refusingAs('damaged_row')`, plain `.parse`, as `demandPolicies` does with `storedWayins`), then returns on the same lifetok. The refusal's `rows.dbhas` is still the whole stored Thing (`storedThingOf`), as `demandPolicies`' is, so a bank damaged outside the lifetok and cited part that also changes the lifetok refuses `damaged_row` at the dbhas, as a gate does under a policy. `Throwers.lifetokNotStored` now takes `ThingRecord | null`, as `gateIssue` and `bornAtNotStored` do.
* **A stored lifetok that fails its check** is damage in a part the write reads, and the write reads it only over a live bank: it refuses `damaged_row` there, as `storedCitedOf` does for a malformed cited part and `demandPolicies` for malformed wayins. Over a tombstone the lifetok is not read, so a rebirth writes over a tombstone whose lifetok is malformed, as safebyok-postgres does (it compares the lifetok in SQL only over a live bank). Set aside: a pick of `am` and `lifetok` together, which refused that rebirth on MemoryVaultDB alone.
* **Battery**: (vaultdb-battery-writes.ts, *the bank*) "carries a bank damaged outside its lifetok forward, under a put that keeps the lifetok", beside the gate's, which fails on MemoryVaultDB with the whole-row read restored; and "rebirths the bank over a tombstone whose lifetok is malformed", `reborn` on both stores.
