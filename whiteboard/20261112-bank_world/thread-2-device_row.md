* **Decisions taken**:
  * The IndexedDB shelf is `<dbName>:devicerow-v001-001-001`, store `devicerow` (const `DeviceRowDBVersion`, was `BankDBVersion`). The stem cannot be `device`: the lease shelf has it. No `oldnames` entry deletes the old `<dbName>:bank-v001-001-001`: a later thread may give a bank its own shelf under that stem, and a delete by exact name would then wipe it on every load. The old database stays in the browser unread; the changeset says so.
  * `fmt` stays 5002, 6002, 7002: `design.md` says the renames of threads 1 and 2 move the three formats once. So `vaultRow-fmt6002.schema.json` (the hidden snapshot under `packages/safebyok/tests/.snapshots`) was rewritten under the same number (its wayin field), and `row-formats.test.ts` is green against it.
  * What a host sees, checked against the code: the new shelf name means `ensureCachedDevice` finds no row and mints a new `device_tok` (the `IdbDeviceDB` battery plants a row in the new shelf, never the old). Leases are NOT affected by this thread: lease rows carry no `device_id`, and the lease shelf keeps its name. What does break is a stored vault row: its wayins have `device_id`, the wayin checks are `.strict()`, so the row reads as damaged, and the field name is also in the wayin's ctx. So the user does not "unlock again": a vault written before is damaged until the host moves the field by hand (the changeset says so). Thread 1's `fmt` bump already refuses those rows, so this adds nothing a host with old data had not already lost.
  * `tests/models/ctx-bytes.test.ts`: the two ctx literals change on purpose (key names `device_tok`, same sort position).
  * `useDeviceTok`'s doc block keeps its old wording (it still says "createOrFind"); only the names moved.
