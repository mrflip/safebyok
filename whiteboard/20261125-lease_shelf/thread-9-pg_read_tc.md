# Thread 9: Postgres mints read_tc (2026-11-25)

Branch `20261125-pg_read_tc`, PR #911, stacked on #905 (thread 2, `20261125-stats`). Proved: `safebyok` lint, typecheck, 32 test files, 2,028 tests; `safebyok-postgres` lint, typecheck, 6 test files, 375 tests (PGlite 0.5.16, which is PostgreSQL 18.6).

* **Built**: every statement `PostgresVaultDB` runs returns `read_tc` as a column, `uuidv7()::text AS read_tc` (`ReadTcSql` in `src/vault-queries.ts`), beside the rows it reads: the get, write (all three kinds), list, birth, get-world and stats statements. `src/postgres-vault-db.ts` takes `read_tc` from the row; `readTcNow` is no longer imported there, and the `Omit<..., 'read_tc'>` row types are gone. The README says `PostgresVaultDB` needs Postgres 18 or later, for `uuidv7()`. Two tests in `tests/postgres-vault-db.test.ts`: two reads in one session are dated in order, and within a second of the database's `clock_timestamp()`; and an answer carries the `read_tc` of the row a fake client returns (which a client-minted `read_tc` would fail).
* **Built, on rework (the Coach: "read_tc is set by the backing store and carried thru after")**: a watch notice carries the database's `read_tc` too.
  * `tell_thing` (`src/vault-functions.ts`) mints `uuidv7()::text` once, as `read_tc`, and puts it in each of the notice's three sizes. `Told` and `toldCheck` carry it through unchecked; `#receivedOrNull` passes it on in `Received`, or, where the notice was too large and the Thing is fetched, the fetch row's own `read_tc`.
  * Core: `Received` (`shapes-answers.ts`) gains `read_tc?: unknown`, raw like its `record`; `ActualChecks.received` picks it (`SeenChecks.readTc.optional()`, refusing `storage_issue`). `AdapterVaultDB.watch` parses it and falls back to `readTcNow()` in one destructuring default; `itemEventOf` takes the `read_tc` as an argument. Memory and IndexedDB send none, so nothing changes for them.
  * Tests: `adapter-vault-db.test.ts`, a received `read_tc` is the notice's, and one made on arrival where none is sent; a non-UUIDv7, uppercase, number or null `read_tc` goes to onBadNews as `storage_issue`. `postgres-vault-db.test.ts`, over PGlite, the event's `read_tc` is the one in the raw NOTIFY text.
* **Decisions made**:
  * `uuidv7()::text`, cast to text so every driver hands back a string; Postgres prints a uuid in lowercase, version nibble 7, variant `[89ab]`, which `ReadTcPattern` accepts (checked against PGlite: `01a211fc-16bf-7000-83c6-...`).
  * One constant, `ReadTcSql`, spliced into each statement, rather than the expression written eight times.
* **Deviations**: the rework touches the core (`Received`, `ActualChecks`, `AdapterVaultDB.watch`), authorized by the orchestrator's rework handoff; the first build stayed inside safebyok-postgres.
  * `Received.read_tc` is typed `unknown`, not `ReadTc`: an adapter hands it raw, as it hands `record`, and the core checks it; a `ReadTc` type would have needed a cast in `#receivedOrNull`. A non-string `read_tc` in a notice therefore refuses `storage_issue` rather than dropping the notice in `toldOf`.
* **Discoveries**:
  * `uuidv7()` runs while the statement executes, after its snapshot is taken: a `read_tc` is now no earlier than the snapshot, where the client's was minted just before the statement. The window is the statement's own milliseconds.
  * `uuidv7()` is monotonic within one backend (connection) only; across a pool's connections, two reads are ordered by the server's clock alone.
  * CI's `postgres` job (e2e) runs only the bankDB battery over real Postgres; `PostgresVaultDB` runs only on PGlite, which is Postgres 18.6, so `uuidv7()` is there.
* **Discoveries, on rework**: a write's notice and its answer each call `uuidv7()` in the same statement, so they carry two different `read_tc`s, a few microseconds apart. Nothing compares them, and no test relies on their order.
